# Проверка внедрения production readiness

Проверено 28 октября 2026 года на ветке `codex/production-readiness` (база Task 9: `01c7cd1`). Этот отчёт фиксирует локальную приёмку задач E1, E2, E4, E5, S1, S2, S4, S5, S8, S10, S11 и S12. Развёртывание на рабочем VPS, внешний S3 и восстановление рабочей базы здесь не выполнялись. Итоговое независимое ревью всей ветки остаётся за главным исполнителем.

Для полного Vitest URL должен указывать только на локальную явно названную тестовую базу с миграциями; пароль и порт в строке выше — пример локального прогона, не параметр проекта. Точные guards интеграционных наборов принимают `autospectrum_final_test` наряду с их собственными именами; они не разрешают произвольную или удалённую базу. Если `INTEGRATION_TEST_DATABASE_URL` не задан, PostgreSQL-наборы штатно пропускаются, поэтому такой прогон не является полным доказательством. `npm run test:production -- --check` отдельно проверяет Docker, установленный Chrome, Compose и временный TLS и завершает работу ошибкой при отсутствии предпосылок. Скрипт использует установленный Chrome channel, не скачанный Chromium.

Production-стек доказал вход обеих ролей через защищённые cookie; запрет сотруднику на аудит и управление аккаунтами; создание, назначение роли, сброс пароля, блокировку и отзыв сессий оператором; видимость разделов панели. Он создал более 50 записей в PostgreSQL и нашёл запись за пределами первой страницы сочетанием фильтров. Через публичный API и браузер проверены завтрашний–60-й день по Москве, отклонение сегодня и 61-го дня, сохранение ровно одной заявки при повторе идемпотентного ключа, конфликт другого payload, действительная бета-копия, 429 с `Retry-After` при меняющемся поддельном XFF, старый `/#/admin` и отмена перехода с грязным черновиком.

Отдельный DNS-пробник остановил и удалил только свой API-контейнер, занял его старый IP и поднял временный echo-upstream с alias `api` по новому IP (`172.19.0.3` → `172.19.0.5`) без перезапуска nginx. Echo-фаза подтвердила сохранение URI и кодированной query-строки, HTTPS forwarding и перезапись поддельных `X-Forwarded-For`/`X-Real-IP`. Затем echo удалён, настоящий API восстановлен по новому адресу, `/api/readyz` снова прошёл через тот же nginx и PostgreSQL. Echo проверяет только маршрутизацию и заголовки; приложение проверяется отдельными реальными тестами выше. После прогона собственные контейнеры, сети, том, временный сертификат и теги образов удалены. Существующий обзорный PostgreSQL-контейнер не затронут.

## Известные ограничения

Шесть оставшихся сбоев общего dev/demo E2E существовали до Task 9 и не скрыты конфигурацией: три фактических переполнения/нарушения раскладки (S6), два устаревших ожидания публичных часов (S7) и один устаревший селектор бренда (S6, сам по себе не доказывает переполнение).

1. `admin.spec.ts`: крупный текст на узком экране панели, S6.
2. `booking.spec.ts`: публичные часы после изменения настроек оператора, старое ожидание строки demo, S7.
3. `booking.spec.ts`: обновление публичной вкладки после изменений настроек в другой вкладке, то же старое ожидание, S7.
4. `booking.spec.ts`: переполнение страницы при крупном тексте на узком телефоне, S6.
5. `booking.spec.ts`: устаревший селектор `.brand-copy strong` в мобильной шапке, S6; это не доказательство переполнения.
6. `booking.spec.ts`: календарь и review при масштабе 400%, S6.

Из утверждённого объёма исключены E3 (валидация некорректного расписания закрытого дня), S3 (глобальный фильтр `conflictsOnly`; он остаётся фильтром текущей страницы), S6 (адаптивность/крупный текст), S7 (публичные часы как расписание дня) и S9 (поле email клиента: сбор в форме, проверка и хранение в заявке). S9 относится к данным заявки, а не к отправке email-уведомлений. Эти пункты не считаются пройденными. Preview-наборы с подменой API проверяют состояние интерфейса, а не запись в PostgreSQL; default dev/demo набор их не запускает, для них даны отдельные команды.

Аудит production-зависимостей выявил moderate `fast-uri` ([GHSA-w74x-v6f9-j3xg](https://github.com/advisories/GHSA-w74x-v6f9-j3xg), [GHSA-wjr9-j795-jxcr](https://github.com/advisories/GHSA-wjr9-j795-jxcr)) и low `fastify` ([GHSA-389g-gv7q-r4x8](https://github.com/advisories/GHSA-389g-gv7q-r4x8)). У текущих маршрутов не обнаружено schema `propertyNames` для уязвимости Fastify или прямого использования untrusted URI нормализации в приложении; это ограниченный анализ применимости, а не доказательство отсутствия риска. Полный audit дополнительно содержит high у dev-инструментов `vite` и `source-map-js`, moderate у `vitest` и `@vitest/mocker`. Версии зависимостей не изменены в рамках данного плана. При первом обращении к registry аудит получил транспортную ошибку; только эта сетевая операция была повторена с разрешённым доступом, затем получен настоящий advisory-ответ. Логи Fastify в тестах и предупреждение Vitest о transform были информативными, не падениями тестов.

Мелкие замечания, переданные на финальную триаж-проверку: `src/data/api.ts:37` сообщает сотруднику ошибку валидации текстом, относящимся к записи; `StaffSection.tsx:21` может объявить успешную запись при неудачном обновлении списка и показать устаревшие данные; `App.tsx:110` продолжает 200-мс interval после нуля countdown до размонтирования. Они не меняют приведённых результатов приёмки.

## Принятые решения по ходу плана

- Реализация задач велась через `subagent-driven-development` согласно выбранному пользователем способу и правилам `AGENTS.md`; `executing-plans` применялся для журнала и проверки. Цена решения — дополнительное ревью каждой задачи, без изменения продукта.
- Изолированный checkout использовал установленный `node_modules` junction при совпадающем lockfile. Риск дрейфа среды закрывался полными тестами и обеими сборками; зависимости не переустанавливались.
- Неподдерживаемый в установленном Fastify 5.12.5 numeric `trustProxy: 1` заменён на `(_address, hop) => hop < 1`, то есть только непосредственный nginx hop. Если топология proxy изменится, правило нужно пересмотреть; тест с поддельным XFF и фактическим nginx выполнен.
- Чистый helper окна записи Task 6 готовился параллельно с Task 3, интеграция ожидала ревью Task 4 из-за общих файлов. Цена возможной ошибки была локальной адаптацией helper; итоговая интеграция и приёмка завершены.
- Инфраструктура smoke Task 9 готовилась параллельно с функциями, а её полная приёмка ожидала их ревью. Это потребовало дополнить harness позднее, но не меняло production deployment или рабочую базу.

Скрипты и README описывают воспроизводимый локальный и VPS-порядок. Никакие рабочие контейнеры, данные, учётные записи или внешние сервисы этим отчётом не объявляются проверенными. Коммит, публикация и итоговое ревью ветки выполняются отдельно главным исполнителем.
